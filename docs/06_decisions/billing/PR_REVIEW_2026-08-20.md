# PR Review — 2026-08-20

> Revisión de los PR #584, #585 y #586.  
> Solo identificación de debilidades y oportunidades de optimización. No se proponen implementaciones ni cambios de código.

## Scope

Reviewed PRs **#584, #585 and #586**, focusing on architectural weaknesses, edge cases, operational risk, maintainability and optimization opportunities.

---

## 🔴 High priority

### PR #585 — Stripe reconciliation can select the wrong subscription

`syncSubscriptionFromStripe()` falls back to the customer's most recent subscription when it cannot find the expected association.

**Risk:** a Stripe customer with multiple historical/active subscriptions could be reconciled against the wrong subscription, potentially overwriting the local `stripeSubscriptionId` and entitlement state.

**What to investigate:** deterministic ownership and identity rules before accepting a Stripe subscription as authoritative.

### PR #585 — One-subscription-per-user can create destructive side effects

The current model can cancel an existing subscription when another subscription is detected for the same user.

**Risk:** a billing operation for one restaurant could affect another restaurant belonging to the same user.

**What to investigate:** whether subscription ownership should be scoped differently and whether cancellation is always safe.

### PR #585 — Checkout race condition remains

Two concurrent checkout requests can both observe that no subscription exists and create separate Stripe Checkouts.

**Risk:** duplicate subscriptions and potentially duplicate charges before reconciliation resolves the local state.

**What to investigate:** whether the one-subscription invariant is actually enforced atomically or only reconciled eventually.

### PR #585 — Stripe is introduced as a synchronous dependency of Billing

Billing can trigger a Stripe reconciliation during page access.

**Risks:**
- Increased latency.
- External dependency failures.
- Unnecessary Stripe traffic.
- Potential polling behaviour under repeated page loads.

**What to investigate:** whether reconciliation should be event-driven, explicitly triggered, cached, or otherwise bounded.

### PR #585 — Reconciliation timestamp semantics may interfere with event ordering

Reconciliation writes `lastEventAt` using the current time rather than necessarily preserving the timestamp of the Stripe event/state being reconciled.

**Risk:** legitimate webhook events could potentially be classified as stale depending on delivery/order semantics.

**What to investigate:** a single, well-defined ordering model for Stripe events and reconciliation.

## 🟠 Medium priority

### PR #585 — Stripe status semantics are distributed across multiple rules

`active`, `past_due`, `paused`, `incomplete` and related states have different entitlement consequences across the billing flow.

**Risk:** Stripe state, local subscription state and UI entitlement state can drift semantically.

**What to investigate:** a single conceptual state machine defining the entitlement outcome of every Stripe status.

### PR #585 — `switchTier()` creates a second billing path

Stripe Portal is intended to be the official customer-facing path, but a programmatic tier-switch implementation remains present.

**Risk:** duplicated billing logic can diverge over time.

**What to investigate:** whether this API is genuinely required or should eventually be removed.

### PR #585 — Tests do not sufficiently target distributed failure modes

Current coverage is stronger around normal behaviour than around concurrency and event ordering.

**Scenarios worth testing conceptually:**

- Concurrent checkout requests.
- Multiple subscriptions.
- Shared Stripe customers.
- Webhook + reconciliation races.
- Out-of-order events.
- Incorrect fallback subscription selection.
- Duplicate cancellation.

### PR #584 — Route-policy exceptions can become the new source of bugs

The centralized route policy is a strong direction, but explicit exceptions remain for actions, uploads and background jobs.

**Risk:** future developers may add a new execution path that bypasses the intended entitlement boundary.

**What to investigate:** how these exceptions are made discoverable and mechanically constrained as the application grows.

### PR #584 — Entitlement checks can happen before rate limiting

Some requests may perform entitlement/DB work before the rate limiter rejects them.

**Risk:** abusive traffic can still consume database resources before hitting the rate limit.

**What to investigate:** ordering of inexpensive request protection versus entitlement resolution.

### PR #584 — `ROUTE_POLICY` can become a maintenance bottleneck

A centralized route map improves consistency but introduces another structure that must remain synchronized with the application routing tree.

**Risk:** growing numbers of routes and exceptions can make the policy increasingly difficult to maintain.

**What to investigate:** whether the policy remains scalable as route count and execution mechanisms grow.

### PR #584 — Compile-time route typing is not the same as runtime enforcement

The design relies on the current SvelteKit routing/execution model.

**Risk:** future framework features or alternative execution paths could bypass assumptions made by the hook.

**What to investigate:** how new SvelteKit primitives or future server execution mechanisms interact with the entitlement boundary.

## 🟡 PR #586 — UI / UX

### Custom location dropdown increases accessibility responsibility

Replacing a native `<select>` with a custom listbox gives visual control but transfers keyboard and assistive-technology behaviour to the application.

**What to investigate:**

- Keyboard navigation.
- Escape behaviour.
- Focus management.
- Active-option semantics.
- Screen-reader behaviour.

### Click-outside handling may not cover the complete interaction model

The dropdown close behaviour is primarily mouse-oriented.

**What to investigate:**

- Escape.
- Keyboard interaction.
- Route changes.
- Mobile drawer transitions.
- Focus restoration.

### Responsive state is duplicated between CSS and JavaScript

The UI uses CSS breakpoints while JavaScript also tracks desktop state through `matchMedia`.

**Risk:** two sources of truth for responsive behaviour.

**What to investigate:** whether both are genuinely necessary.

### Custom dropdown positioning can be more fragile than native controls

The menu lives inside a scrolling/sidebar context.

**Risk:** overflow, stacking-context or small-viewport edge cases.

**What to investigate:** behaviour under sidebar scrolling, mobile layouts and constrained viewport heights.

---

# Overall assessment

## PR #584

**Direction: strong.**

Centralizing entitlement policy is materially better than relying on scattered manual checks.

The main future risk is the growth of explicit exceptions and maintaining the policy alongside the routing system.

## PR #585

**Highest-risk PR.**

The difficult part is not Stripe API integration itself. It is the distributed consistency model between:

`Stripe → webhooks → database → reconciliation → entitlement`

The fallback subscription selection and concurrency model deserve particular scrutiny before relying on this as a billing invariant.

## PR #586

**Low architectural risk.**

Main concerns are accessibility and the additional complexity introduced by replacing native browser behaviour with a custom control.

3. Define a single Stripe-status → entitlement state model.
4. Test webhook/reconciliation ordering and concurrency scenarios.
5. Validate the custom dropdown's complete accessibility behaviour.
6. Reassess the scalability of route-policy exceptions as the application grows.
